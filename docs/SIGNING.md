# Code signing NoteCraft

Signed builds need a certificate **issued to you**. A signing key cannot be
generated by an assistant or checked into the repository: Windows trusts
certificates chained to a public CA (or Microsoft's Trusted Signing service),
and macOS trusts only Apple Developer ID certificates tied to your Apple
Developer account. Anything self-made is untrusted and still triggers
SmartScreen / Gatekeeper warnings.

This document lists what to obtain, which GitHub secrets to store, and how the
`*_release.yml` workflows use them.

---

## Windows (Authenticode)

Pick one:

### A. Azure Trusted Signing (recommended for CI, no hardware token)

1. Create an Azure Trusted Signing account and a certificate profile
   (<https://learn.microsoft.com/azure/trusted-signing/>). Identity validation
   usually completes in a few business days.
2. Create an Entra app registration with access to the account; note the
   tenant id, client id and client secret.

Secrets to add (Settings → Secrets and variables → Actions):

| Secret | Value |
| --- | --- |
| `AZURE_TENANT_ID` | Entra tenant id |
| `AZURE_CLIENT_ID` | App registration client id |
| `AZURE_CLIENT_SECRET` | App registration secret |
| `AZURE_ENDPOINT` | Trusted Signing endpoint, e.g. `https://eus.codesigning.azure.net/` |
| `AZURE_CODE_SIGNING_ACCOUNT` | Trusted Signing account name |
| `AZURE_CERTIFICATE_PROFILE` | Certificate profile name |

`windows_release.yml` detects `AZURE_CODE_SIGNING_ACCOUNT` and builds with a
`signCommand` override that calls [`trusted-signing-cli`](https://github.com/azure/trusted-signing-action).
Without the secret the build is simply unsigned.

### B. OV/EV code-signing certificate (PFX + hardware token or HSM)

Buy from a CA (DigiCert, Sectigo, SSL.com, …). Modern OV/EV certs ship on a
hardware token or cloud HSM, which cannot be exported as a PFX for CI; host it
with the CA's signing service or use option A instead.

If you have an exportable PFX:

| Secret | Value |
| --- | --- |
| `WINDOWS_CERTIFICATE` | base64 of the `.pfx` (`base64 -w0 cert.pfx`) |
| `WINDOWS_CERTIFICATE_PASSWORD` | PFX password |

Then import it on the runner before building:

```powershell
$pfx = [IO.File]::WriteAllBytes("$env:RUNNER_TEMP\cert.pfx", [Convert]::FromBase64String($env:WINDOWS_CERTIFICATE))
certutil -f -p $env:WINDOWS_CERTIFICATE_PASSWORD -importPFX $pfx NoExport
```

and set the thumbprint in `tauri.conf.json`:

```json
"bundle": {
  "windows": {
    "certificateThumbprint": "AB12…",
    "digestAlgorithm": "sha256",
    "timestampUrl": "http://timestamp.digicert.com"
  }
}
```

### C. Self-signed certificate (testing only)

Works for local installs and CI smoke tests but **does not** remove the
SmartScreen warning for anyone else:

```powershell
New-SelfSignedCertificate -Type CodeSigningCert -Subject "CN=NoteCraft Dev" `
  -KeyUsage DigitalSignature -CertStoreLocation Cert:\CurrentUser\My
```

## macOS (Developer ID + notarization)

1. Enrol in the Apple Developer Program (paid, annual).
2. Create a **Developer ID Application** certificate in the Apple Developer
   portal, download it, and export the certificate *and* private key as a
   `.p12` with a password.
3. `base64` the `.p12` (`base64 -i cert.p12 | pbcopy`).
4. Create an app-specific password for notarization
   (<https://appleid.apple.com> → Sign-In and Security).

Secrets:

| Secret | Value |
| --- | --- |
| `APPLE_CERTIFICATE` | base64 `.p12` |
| `APPLE_CERTIFICATE_PASSWORD` | `.p12` export password |
| `APPLE_SIGNING_IDENTITY` | e.g. `Developer ID Application: Your Name (TEAMID)` |
| `APPLE_ID` | Apple account email |
| `APPLE_PASSWORD` | app-specific password |
| `APPLE_TEAM_ID` | 10-character team id |

`macos_release.yml` passes these to `tauri build`; the Tauri CLI imports the
certificate into a temporary keychain, signs the bundle and submits it for
notarization + stapling. With no secrets set the DMG is unsigned.

Ad-hoc signing (`codesign -s -`) is a local-development convenience and does
not satisfy Gatekeeper for distributed builds.

## Linux

`.deb` and `.AppImage` are not OS-signed; distributions trust repository
metadata instead. If you publish an apt repo, sign the `Release` file with GPG
(`gpg --detach-sign --armor Release`). For checksums, generate
`SHA256SUMS` alongside the artifacts.

## Auto-updater signatures (optional, unrelated to OS trust)

If the app later ships `tauri-plugin-updater`, its bundles carry a minisign
signature generated from a keypair *you* own:

```bash
bun run tauri signer generate -w ~/.notecraft/updater.key
```

Keep the private key out of git, store it as the `TAURI_SIGNING_PRIVATE_KEY`
secret (base64) with `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, and put the printed
public key into `tauri.conf.json` → `plugins.updater.pubkey`. This key signs
update payloads only; it does not make installers trusted by Windows/macOS.

## Verifying a signed build

```powershell
# Windows
Get-AuthenticodeSignature .\NoteCraft_0.1.0_x64-setup.exe | Format-List Status, SignerCertificate
```
```bash
# macOS
codesign --verify --deep --strict --verbose=2 NoteCraft.app
spctl --assess --type execute --verbose NoteCraft.app
xcrun stapler validate NoteCraft_0.1.0_aarch64.dmg
```

## Updater signing key

Release bundles are signed with a Tauri minisign key so the updater only installs builds you
produced. The keypair for this repository was generated with:

```bash
bun run tauri signer generate -w .tauri-keys/notecraft-updater.key --password ""
```

- Public key: embedded in `src-tauri/tauri.conf.json` under `plugins.updater.pubkey`.
- Private key: stored as the `TAURI_SIGNING_PRIVATE_KEY` repository secret.
- `.tauri-keys/` is gitignored and must never be committed.

Every build workflow passes `TAURI_SIGNING_PRIVATE_KEY` to `tauri build`, which produces the
`.sig` files next to the updater archives. Rotate the key by generating a new pair, updating the
public key in the config, and replacing the secret; installed copies then stop accepting updates
signed with the old key.
